Why it isn't a 4 (scalability)
- Polling cost grows with every task ever created. The UI calls /api/state every second. That returns all tasks with no paging, and each task costs two extra queries (assigneeJson, service.js:435). Completed tasks are kept forever (D25), so the list only grows.
- The ticker scans tables every 100 ms (service.js:183). There are no indexes on tasks(status) or assignments(status, offer_expires_at) to make those scans cheap.
- Every routing request loads every contributor and parses their keywords in JavaScript (eligibleFor, service.js:68). Keywords are stored as JSON text, not in a join table.
- service.js does everything in 568 lines: routing, timers, restart recovery, seeding, validation, actions and read models.
- Transaction state is shared by the whole module (db.js:109-110), so the code assumes one database per process.
- Some values are written out by hand in several places. The priority list appears in service.js:4 and again in the database schema (db.js:13). Status names like 'offered' and 'accepted' are typed directly into many queries.
All of this is acceptable under D14, which asks for a simple stack. It just isn't "highly scalable".
